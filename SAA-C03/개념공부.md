
# Lambda
이 코드를 실행해줘라고 요청할때만 잠깐 켜졌다 사라지는 실행 서비스

1. 15분 실행 제한이 있으니 처리에 그 이상의 시간이 걸리면 Lambda를 제외하고
   ECS/Fargate 나 AWS Batch를 고르자
   
2. vpc에 붙은 Lambda는 인터넷에 나가려면 NAT 게이트웨이가 필요하고 S3,DynamoDB에는
   vpc 엔드포인트로 무료로 나가자
   
# ECS
여러 개의 도커 컨테이너를 언제 어디서 실행하지 지시하고 관리하는 관제 서비스

1. 시작유형이 EC2면 직접 관리하고, Fargate면 서버관리가 사라진다.

2. 태스크 vs 실행
   태스크 역할은 컨테이너 안의 애플리케이션이 S3 등 AWS API를 호출할때 쓰는 권한이다.
   실행 역할은 ECR에서 이미지를 당기고 CloudWatch에 로그를 쓰는 권한이다.

3. ALB 와 동적 포트 매핑
   하나의 EC2에 여러개의 같은 컨테이너를 띄울려면 ALB의 동적 포트 매핑을 사용한다.
   동적 포트 매핑이란 한개의 EC2 서버에 3개의 같은 컨테이너가 들어온다치면 
   이름은 같지만 포트를 자동으로 다르게 배정하고 ALB가 그 포트들을 알아서 찾아간다.

# Fargate
컨테이너를 서버 관리 없이 실행해 주는 서비스, ECS나 EKS에서 컨테이너를 돌릴때
EC2 서버를 직접 준비하고 관리해주는 대신, 컨테이너가 필요한 CPU와 메모리만 지정해주면
AWS가 알아서 실행해준다.

1. Lambda 와의 선택 기준
   둘 다 서버리스지만 Lambda는 15분/이벤트 기반, Fargate는 장시간 실행/상주 서비스이다.
   "컨테이너 이미지를 그대로 써야한다", "15분을 넘는다" 면 Fargate를 사용한다.
   
2. 비용관련
   Fargate는 비용이 높고 상시 돌아가는 워크로드에서는 EC2 시작유형보다 비싸다.
   "가장 저렴" 을 물으면 EC2 시작유형이 답이 될 수 있다.

# AMI 이미지
EC2 인스턴스를 부팅할 때 쓰는 틀( 설치된 OS, 소프트웨어, 설정을 통째로 얼려놓은 이미지 파일)
다른 리전에서 쓰려면 복사해야된다.

1. 부팅 시간 단축
   "확장이 너무 느리다" 는 문제에서, 매번 패키지를 설치하는 대신 필요한 소프트웨어를 미리 포함한
   AMI를 만들어 두는 것이 정답
   
2. 리전 간 복사와 공유
   AMI는 리전에 종속되므로 다른 리전에 쓰일려면 복사해야한다. 
   재해 복구나 다중 리전 배포 문제에서 "AMI를 대상 리전으로 복사" 가 필요한 단계로 등장한다.

3. 보안 문제
   AMI ID는 리전마다 다르므로 복사 후 새 ID를 사용해야 한다.
   민감 정보를 담은 채 AMI를 공유하는 것은 피해야한다.


# 약정 할인
예약 인스턴스, Savings Plan / 서비스를 1~3년동안 꾸준히 사용

1. 1~3년 동안의 기한동안 꾸준히 쓰겠다 약속하는 것

2. 예약 vs Savings Plan
   예약 인스턴스는 특정 인스턴스에 묶이지만 Savings plan은 유연한 편이다.

# EKS
쿠버네티스라는 오픈소스 컨테이너 관리 시스템의 두뇌(컨트롤 플레인) 부분을 AWS가 대신 운영해준다.

1. 구분 신호
   문제에 Kubernetes, kubectl, Helm, 기존 k8 매니페스트 같은 단어가 있으면 EKS
   단순히 컨테이너라고만 한다면 ECS/Fargate가 운영부담이 더 적다.

# Beanstalk
Elastic Beanstalk 는 코드만 올리면 뒤에서 EC2/로드밸런서/오토스케일링 같은 자원들을 알아서 조립해주는
관리형 배포 서비스이다.

1. 구분 조건
   "개발자가 인프라를 신경쓰지않고 웹앱을 올려야 한다" 는 조건에 대응한다.
   하지만 컨테이너 중심 문제는 ECS/Fargate 가 , 완전 서버리스 조건에서는 Lambda/API Gateway가
   정답일 수 있다.

# AWS Batch
대량의 작업 목록을 넣으면 그때그때 필요한 만큼 EC2나 Fargate 용량을 불러왔다가 끝나면 알아서 치워주는
관리형 작업 스케줄링 서비스이다. 대량 처리에 적합하다.

1. 스팟 + Batch
   "야간 배치 + 최저 비용" 조합의 정답이다.

2. Lambda와의 구분
   짧고 이벤트 기반이면 Lambda, 길고 대량이며 의존성이 무거우면 Batch

# 배치그룹
이미 만든 EC2 인스턴스들을 물리적으로 어떻게 나란히 놓을지 지정하는 설정값
목적이 최저지연시간, 동시 장애 회피인지에 따라 세 종류중 하나를 고르는 문제로 나온다.

1. Cluster - 최저 지연시간
   단일 AZ안에 인스턴스를 밀집시켜 지연을 최소화한다. 대신 AZ가 하나 죽으면 다 죽는다.
   고가용성에 부적합하다.

2. Spread - 최대격리
   인스턴스마다 별로 랙에 배치해 하드웨어 장애가 겹치지 않게 한다. 
   AZ당 7개 인스턴스 제한이 있어 소수 중요 인스턴스에 배치한다.
   대규모 클러스터로는 구성이 불가능하다.

3. Partition - 분산 시스템
   인스턴스를 파티션 그룹으로 나누고 파티션끼리 하드웨어를 공유하지 않게한다.


# 버전관리 / 오브젝트 락
파일을 덮어쓰거나 지워도 예전 기록을 남겨놓는다. 
Object Lock 이랑 쓰면 정해진 기간동안 누구도 지울 수 없다.

1. 실수 삭제 복구
   "실수로 지운 파일을 복구하고 싶다" 의 정답이다.

2. MFA Delete
   루트 사용자만 설정 가능하며, 악의적 삭제 방지에 쓰인다.

3. Object Lock 의 두가지 모드
   거버넌스 모드 → 특별 권한이 있으면 해제 가능
   컴플라이언스 모드 → 누구도 삭제 못함

# RDS
MySQL/PostgreSQL 같은 기존 데이터베이스 엔진을 AWS 가 대신 설치/패치/백업 까지 해주는 관리형 서비스

1. Multi-AZ 는 고가용성 전용
   "읽기 성능 향상" 이면 Multi-AZ는 오답이다

2. RDS Proxy 로 연결 폭주 완화
   Lambda나 오토스케일링 그룹처럼 수시로 뜨고 내려가는 구조에서는 연결 수가 폭주해 오류가 날 수 있다.
   RDS Proxy 가 연결 풀을 대신 관리해 이것을 완화해준다.
   "Lambda 동시 실행이 늘면서 DB 연결이 고갈된다" 하면 프록시가 정답이다.

# DynamoDB
저장공간이 무한히 늘어나는 밀리초 지연 서버리스 데이터베이스이다. 

1. DAX로 읽기 캐싱
   읽기가 지배적이고 마이크로초 지연이 필요하면 DynamoDB Accelerator(DAX) 를 앞에 둔다.
   애플리케이션 코드 변경이 거의 없다.

2. Global Tables
   여러 리전에 다중 쓰기가 가능한 복제 테이블을 만들어 전 세계 사용자에게 낮은 지연을 제공한다.

# Aurora
데이터를 3개의 AZ에 2개씩해서 총 6개의 복제본을 가진다. 그래서 AZ하나가 통째로 죽어도 안전하다.
고가용성/ 읽기 확장이 큰 규모/ 사용량이 들쭉날쭉한 개발환경 비용절감이 대표적 신호이다.
MySQL/PostgreSQL 호환만 지원한다.

1. Aurora Serverless v2
   "가끔만 쓰는 개발" , "테스트 비용 절감" 에 적합하다.

2. 복제본 최대 15개
   Aurora 복제본은 같은 스토리지를 공유해서 복제 지연이 매우 짧다. 거의 실시간이다.

# ElastiCache
자주 찾는 정보를 데이터베이스 앞에 미리 꺼내놓는 임시 저장소이다.
반복조회가 나올때 쓰인다.

1. Redis vs Memcached
   Redis → 고가용성, 영속성, 복제, 자동 장애 조치, 정렬 집합 같은 자료 구조를 지원
   Memcached → 단순 캐시이며 멀티 스레드로 수평 확장만 한다.

2. 쓰기가 지배적인 구조에 x
   데이터가 계속 바뀌므로 캐시가 별 도움이 안된다.

# 보안 그룹 / NACL
누구를 들여보내고 막을지 정해두는 가상의 규칙 목록이다.
보안 그룹 → 한번 들어오면 나갈때 다시 검사하지 않는다.
NACL → 들어올 때는 나갈 때든 매번 검사한다.

1. 차단은 NACL 로만
   보안그룹에는 거부 규칙이 없다.

2. NACL 에서 인바운드만 열고 아웃바운드 임시 포트를 잊는 것
   요청은 들어오지만 나가질 못한다. → 아웃바운드 규칙을 추가하자

# Route53 DNS
도메인 이름을 실제 주소로 바꿔주는 관리형 전화번호부 서비스이다.

1. 라우팅 정책 구분
   Latency(지연시간) → 가장 빠른 리전으로
   Geolocation(지리 위치) → 사용자의 위치 기준
   Weighted(가중치) → 비율 (카나리 배포)
   Failover(장애 조치) → 상태 확인 실패 시 대기 사이트로 이동

2. 데이터 복제 없이 재해 복구
   Route53 장애조치 만으로는 불가능하다.

# VPN 연결 (Site-to-Site VPN)
이미 있는 공용 인터넷 위에 암호화된 가상의 터널을 뚫어 온프레미스와 vpc을 잇는 방식

1. Direct Connect 와의 선택
   "빠르게 연결", "저렴하게" → VPC
   "일관된 대역폭", "예측 가능한 지연시간", "대용량 상시 전송" → Direct Connect

2. Direct Connect 의 백업
   전용선이 끊겼을 때는 대비한 이중화 수단으로 VPN 을  함께 구성한다.

# Direct Connect
온프레미스 시설과 AWS 사이에 실제로 깔리는 인터넷을 거치지 않는 물리 전용 회선이다.
구축에 몇 주에서 몇 달이 걸린다.

1. 구축 기간이 함정
   "이번 주 안에 해결해야 한다" 라는 조건이 있으면 VPN이 정답

2. 이중화 구성
   고가용성을 생각할려면 다른 로케이션에 회선을 두거나 VPN 백업을 붙여야한다.

# Global Accelerator
전 세계 어디서 접속해도 가장 가까운 AWS 엣지에 라우팅된다.
콘텐츠를 캐싱하지않고 전용 고속도로를 타는것과 비슷하다.

1. CloudFront 와의 비교
   캐싱 가능한 정적/동적 HTTP 콘텐츠 → cloudfront
   TCP/UDP, 게임, 고정IP → Global Accelerator

2. 리전 장애 조치가 빠르다

# VPC 피어링 연결
두 VPC 사이에 사설 경로를 만드는 것이다.
전이적 라우팅이 불가능하다. (A-B, B-C 가 있으면 A가 B를 통해 C와 연결은 하지 못함)

1. VPC 갯수
   두 세개 → VPC 피어링
   수십개 → Transit Gateway
